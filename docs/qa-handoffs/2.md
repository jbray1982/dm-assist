# QA Handoff — Issue #2: Implement Dice Roller MVP

Branch: `feature/issue-2`
Spec: `docs/dice-roller/001-mvp-spec.md`
Design: `handoffs/design-2.md` (see §10a for the D3/D4 product-owner reversals — reason input
and advantage/disadvantage toggle are both in scope for this MVP)
Review: `handoffs/review-2.md` (status: approved, post-fix)

## Summary

This is the repository's first shipped code: a C# dice engine (`DmAssist.Dice`), an ASP.NET
Core API (`POST/GET/DELETE /api/rolls` on `http://localhost:5178`), and a Vite/React frontend
(`web/`). Automated coverage is green (68 backend + 32 frontend tests) and covers the engine's
grammar, error codes, and pure logic thoroughly. It cannot see two things: how the page actually
renders, and whether a synthesized sound fires in a real browser. The review's two blocking
findings — a spacing-token naming mismatch that left every component's padding/gaps unresolved,
and an unhandled-exception path that turned a fat-fingered dice count into a raw 500 instead of
a 400 — were both real bugs that no test caught, and both are now fixed in-branch. This handoff
is scoped to the things only a loaded page can prove: the two fixes hold up live, the DM roll
flow works end to end, and the two reversed-into-scope features (reason, advantage/disadvantage)
behave correctly. No regression sweep of anything else — there is no "anything else" yet.

Files changed: `src/DmAssist.Dice/**`, `src/DmAssist.Api/**`, `web/src/**` (full file list in
`handoffs/manifest-2.md`).

## Setup

1. `dotnet run --project src/DmAssist.Api` — API on `http://localhost:5178`.
2. In a second terminal: `cd web && npm install && npm run dev` — Vite dev server, `/api`
   proxied to the API above. Open the printed local URL in a browser.

## Test steps

1. **Load the app.** Open the dev server URL. Expected: the page renders in the Scroll theme —
   sepia/parchment background, no unstyled/default-browser look, no console errors. This is the
   first real load of the repo's first UI; confirm it isn't blank or broken.

2. **Spacing/layout check (regression guard for the token-naming bug the reviewer caught).**
   Look at the roll builder panel, the number pad, and the roll log side by side. Expected:
   visible, consistent gaps between fields/buttons and padding inside panels and buttons —
   nothing crammed edge-to-edge or overlapping. (This was the critical bug: components
   referenced `--space-xs/sm/md/lg` while `tokens.css` only defined `--space-1..5`, so every
   gap/padding silently resolved to nothing. It's fixed by renaming the token scale — this step
   confirms the fix actually renders correctly, not just that the CSS variable names now match
   textually.)

3. **Number-pad build flow.** Click the "Count" button under the pad, tap a couple of digits;
   click "Sides", tap digits; click "Mod", tap digits. Expected: the expression field above
   updates live to match (e.g. building count=2, sides=8, mod=3 shows `2d8+3`). Click **Roll**.
   Expected: a result card appears showing each die face as a chip and the total.

4. **Expression typing populates the builder.** Clear the expression field and type `27d3+4`.
   Expected: the builder's count/sides/modifier fields update to 27/3/4 (builder stays enabled,
   not greyed out).

5. **Advanced expression disables the builder but still rolls.** Type `4d6kh3` into the
   expression field. Expected: the builder fields and the number pad grey out/disable, while the
   expression field remains editable. Click **Roll**. Expected: it still rolls successfully,
   showing 4 dice with exactly 3 undropped and 1 struck-through (see step 9), and clearing the
   expression back to something simple (e.g. `d20`) re-enables the builder.

6. **Invalid input — missing sides (`1d`).** Type `1d` into the expression field and try to
   roll. Expected: a 400 error message renders under the field with a caret/marker at the
   position right after the `d` (where a sides number was expected) — not a blank screen, crash,
   or generic browser network error.

7. **Invalid input — oversized selector (`2d6kh3`).** Type `2d6kh3` and roll. Expected: an error
   message (selector keeps more dice than were rolled) with a position marker under the
   expression.

8. **Invalid input — dice cap exceeded (`1001d6`).** Type `1001d6` and roll. Expected: an error
   message for the dice-cap violation, with the position caret pointing at the start of `1001`
   (not at `d` or the end of the string). This is the reviewer's second critical fix — confirm
   it's a clean 400 with a message, not a crash or a hung request.

9. **Dropped dice render struck through.** Using the `4d6kh3` result from step 5 (or roll it
   again), expected: the 3 kept dice render normally and the 1 dropped die renders with a
   strikethrough/dimmed style, with the total reflecting only the kept dice.

10. **Reason input round-trips to the log.** Type a reason (e.g. "Attack roll") into the reason
    field, then roll a simple expression (e.g. `d20`). Expected: the newest log entry shows the
    reason text alongside the expression and total. Clear the reason field (leave it blank or
    whitespace-only) and roll again. Expected: that log entry shows no reason line at all (blank
    reason must not appear as an empty line or literal "null").

11. **Advantage/disadvantage toggle rewrites the expression.** With a single-die roll built (e.g.
    `d20` via the builder), click the advantage toggle's "up" option. Expected: the expression
    field updates to `2d20kh1`. Click the "down" option. Expected: it updates to `2d20kl1`. Click
    the neutral option. Expected: it returns to `1d20`/`d20`. Roll each state and confirm it
    executes without error.

12. **Toggle disables when not toggle-representable.** Using the number pad, set count to 2 (a
    two-die roll, e.g. `2d8`). Expected: the advantage/disadvantage toggle buttons become
    disabled (visibly greyed, not clickable) because the toggle only applies to single-die rolls.
    Set count back to 1 and confirm the toggle re-enables.

13. **Log ordering and clearing.** Perform 3–4 rolls in a row. Expected: the log lists them
    newest-first (the most recent roll at the top). Click the log's **Clear** button. Expected:
    the log empties immediately with no confirmation prompt.

14. **Sound plays on success, not on error.** After the page has registered at least one user
    gesture (e.g. any click so far satisfies the browser autoplay policy), roll a valid
    expression. Expected: an audible dice-rattle sound plays. Then trigger an invalid roll (e.g.
    `1d` from step 6). Expected: no sound plays on the error path.

If all of the above pass, that proves issue #2 is complete.

## Edge cases

- Typing `d20` (no explicit count) and rolling: expected to behave as `1d20` and the logged/
  normalized expression should read `1d20`.
- Typing a fully advanced, non-builder expression with parentheses/arithmetic (e.g. `(2d6+3)*2`)
  should also grey out the builder and still roll correctly.
- Rolling with the reason field containing only spaces should log as if no reason were given
  (same as step 10's blank case) — the trim-to-null normalization happens once, in `useRoller`.
- Rolling more than 100 times in one session (if time permits) should drop the oldest entries
  off the bottom of the log, keeping the 100 most recent, newest-first.

## Impact note

None. This is the project's first shipped feature — there is no pre-existing content or
behavior for this change to invalidate.
